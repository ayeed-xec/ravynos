# Decisions

Each entry records one design decision: what was chosen, what else was considered, and
why. [SYSTEM-DESIGN.md](SYSTEM-DESIGN.md) states only the outcome and cites the entry.
An entry is changed by adding a new entry that supersedes it, never by editing history.

Status is one of **accepted** (in force) or **proposed** (awaiting the project owner).

---

### ADR-01 — Compatibility target

**Accepted.** User-space ABI target: macOS 27.2.1, build 26B131, and the XNU line it
ships with (xnu-13432). Kernel of record until that source is published:
xnu-12377.121.6, vendored. When Apple publishes the newer tag, it replaces the vendored
tree and the patch series is rebased.

The corresponding Darwin release is 26.2 (`kern.osrelease` 26.2.0): Apple's build
numbers carry the Darwin major version as their prefix (build 26B131), and the vendored
xnu-12377 line is Darwin 25, shipped with macOS 26. Earlier documents that say Darwin 27
are wrong.

### ADR-02 — The SDK targets the macOS platform

**Accepted.** Binaries built with the ravynOS SDK carry `LC_BUILD_VERSION` platform
macOS, Apple's install names, and Mach-O format. `SDKSettings.json` declares the macOS
platform; the SDK's name and display name say ravynOS.

*Rejected:* a distinct `ravynos` platform. It would make apps built with our SDK differ
from the apps we must run, and every platform check in dyld, the frameworks and the
kernel would fork.

### ADR-03 — Target triples

**Accepted.** Harness names (`x86_64-ravynos`, `arm64-ravynos`, `riscv64-ravynos`) map
to clang triples `x86_64-apple-macosx<min>` and `arm64-apple-macosx<min>`. riscv64 needs
an LLVM patch adding a Darwin-family Mach-O target; until it exists, riscv64 user space
is not built.

*Rejected:* `<arch>-ravynos` passed to clang — clang emits ELF for an unknown OS.
`<arch>-unknown-unknown-macho` — loses every Darwin default the frameworks rely on.

### ADR-04 — Linkers

**Accepted.** `ld64.lld` for executables, dylibs and frameworks. Apple's `ld64` (APSL,
built in stage 1) for fully static executables and for the kernel and kernelcache links,
which use options `ld64.lld` 18 does not implement (`-static`, `-kernel`, `-alias_list`,
`-r`). Until stage 1 builds `ld64`, `ld64.lld` may link test kernels and anything else it
can produce correctly.

### ADR-05 — Objective-C runtime

**Accepted.** Apple's objc4.

*Rejected:* libobjc2 (MIT). It does not decode the metadata current Apple compilers emit
for Mac binaries, so it cannot run existing apps. `Docs/OBJC-RUNTIME-AUDIT.md` is
superseded by this entry.

### ADR-06 — launchd and XPC

**Accepted.** launchd seeded from Apple's open-source launchd-842 (Apache-2.0). libxpc is
our own, implementing Apple's public API with our own wire format, because both ends of
every XPC connection on ravynOS are our code.

### ADR-07 — Window server protocol

**Accepted.** The protocol between SkyLight and WindowServer is private and ours.
Compatibility is achieved in the client frameworks and in SkyLight's exported functions,
which applications call; no application observes the wire.

### ADR-08 — Order of closed-source applications

**Accepted.** A small AppKit app, then a Qt app, then a SwiftUI app, then an Electron app.
The set, confirmed against each application's current architecture and toolkit before W6
starts: The Unarchiver (AppKit), TeamViewer (Qt), a SwiftUI-only application from the
same review, and Slack (Electron). An application that no longer fits its rung is
replaced by another that does, and this entry is amended.

*Rejected:* Electron first. Chromium uses more of macOS than almost any other
application (its sandbox, cross-process layers, Metal through ANGLE, keychain, code
signature checks) and would block on everything at once.

### ADR-09 — The kernel builds inside `rv`

**Accepted.** XNU is an `rv` component. Its configuration is generated by XNU's own
`SETUP/config` from the `MASTER` files; mig and system-call tables are generated at
build time; compile and link steps join the single ninja graph.

*Rejected:* a separate kernel build driver with hand-written configuration headers. It
drifts from XNU's real configuration and splits the build in two.

### ADR-10 — Vendored trees stay pristine

**Accepted.** No edits are committed inside a vendored tree. Every change is a patch file
with `why:`/`fate:` headers; generated files are build outputs. CI compares each vendored
tree with its upstream tag.

### ADR-11 — arm64 board

**Accepted.** A new board configuration, `RVVIRT`, derived from XNU's `VMAPPLE`: GICv3,
PL011, generic timer, PSCI, 16K pages. Changes from VMAPPLE: built for the `arm64` ABI,
not `arm64e`, with Apple pointer authentication off; the paravirtual PAC hypercalls
removed; the read-only-region (`rorgn_*`) functions, whose Apple sources are not
published, provided by our code; the classic (non-SPTM) pmap selected through XNU's
configuration; our code in place of Apple's closed board library. QEMU runs it with
`-cpu max`, which provides the 16K translation granule.

*Rejected:* writing a new arm64 pmap and exception layer — XNU already has both.
Booting `VMAPPLE` unchanged on QEMU — it calls Apple's hypervisor, which QEMU on Linux
does not provide.

### ADR-12 — Cryptography

**Accepted.** BoringSSL, chosen over BearSSL because it covers TLS 1.3, Ed25519 and the
modern primitives applications and updaters expect. It is vendored once at
`Foundation/boringssl/` (S29 owns it); the kernel's `libcc_kext` (S05) compiles the
subset the kernel needs from the same tree. Its files carry ISC, OpenSSL/SSLeay or
Apache-2.0 terms, all permissive (ADR-24); a per-file license check runs in the audit. It provides the
primitives behind `cc_kext` in the kernel, CommonCrypto and the Security framework in
user space, and TLS. Apple's corecrypto is not used: its license is not an open-source
license. The choice of library is the first implementation task of S05's `cc_kext`
replacement.

### ADR-13 — Apple's proprietary SDK

**Accepted.** Never a build input, never in the repository, never required. Headers and
`.tbd` files from it are not copied or derived from. Our headers are written by us; our
stubs are generated from our libraries.

### ADR-14 — Foreign drivers and GPL code

**Accepted.** FreeBSD and Linux drivers run natively in our kernel or in a user-space
driver host, behind interfaces we write (BSD-2-Clause). Permissively licensed drivers
live in this repository. Sourcing order: native IOKit drivers; BSD- and ISC-licensed
drivers from FreeBSD, OpenBSD and NetBSD; Linux drivers available under a permissive
license or a permissive option of a dual license. The supported hardware list must be
reachable with these alone (ADR-24). GPL-only drivers are an optional last resort: they
live in a separate repository, are built against our published driver kit, are installed
by the user from an opt-in channel, and never enter this repository, its builds, the
shipped image, or any tier.

### ADR-15 — Languages

**Accepted.** C, C++ and Objective-C wherever code must match Apple's
binaries or is vendored. Rust for new system services with no Apple ABI to match (the
window server, `rv`, new tools). The bootloader: the existing C loader in `Boot/loader/`
is kept and fixed rather than rewritten in Rust; it is small, freestanding and already
runs on three architectures.

APFS (S19) is written in Rust: one `no_std` crate, `apfs-core`, holds the on-disk format
and is used by the user-space tools, by the kernel file system (a kext whose thin C layer
implements XNU's VFS and vnode callbacks and calls the crate), and by the bootloader's
read-only reader (the crate built as a static library for the UEFI targets, linked into
the C loader). Parsing untrusted on-disk structures is where Rust's bounds and lifetime
checks pay most.


### ADR-16 — Fonts

**Accepted.** Fonts may be under the SIL Open Font License or another permissive
license. Fonts under GPL or AGPL, even with a font exception, are removed. Apple's fonts
never ship; applications' font names are mapped to ours.

### ADR-17 — The license rule covers the whole repository

**Accepted.** No GPL, LGPL or AGPL file anywhere, `Legacy/` included, including build
scripts (`config.guess`, `config.sub`, m4 macros) and files generated by GPL tools. The
license audit scans the whole tree. Vendored upstream trees are not edited, so where one
ships a Bison-generated file (XNU's `OSUnserialize*.cpp`, migcom's `parser.c`), the
build regenerates it from its grammar with byacc and never compiles the shipped copy.

### ADR-18 — Apple Silicon hardware

**Accepted.** Apple Silicon Macs are a later target. They boot through Apple's
documented boot-policy method with our own stage-1 loader. Asahi Linux's m1n1 changed
from MIT to GPLv2 at version 2.0.0, so its code is not read for our loader; its method,
published in Asahi's documentation, may be followed.

### ADR-19 — Architectures

**Accepted.** arm64 and x86_64 are both primary: every tier must pass on both, and CI
builds and boots both on every push. riscv64 is secondary: it runs as a track and gates
no wave. Current Mac software ships arm64 or universal; x86_64 keeps PCs and older
software in reach.

### ADR-20 — x86_64 processors

**Accepted.** XNU's x86 code panics on processors it does not recognize
(`osfmk/i386/cpuid.c`) and calibrates its time base from Intel model-specific registers
(`osfmk/i386/tsc.c`). QEMU runs an Intel CPU model with an invariant TSC and the
hypervisor timing leaves. Support for AMD processors is a permanent patch to those two
files, part of S06.

### ADR-21 — XNU's host tools

**Accepted.** XNU's build expects bison, flex, csh and Apple's `xcrun` tools. We build
its `SETUP/config` tool with byacc and a hand-written scanner (as a patch), implement
`doconf`'s logic in `rv` instead of running the csh script, use `unifdef` (BSD), and do
not produce CTF debugging data, so `ctfconvert` and `ctfmerge` are not needed.

### ADR-22 — Older APSL and CDDL in vendored Apple code

**Accepted.** Apple's own releases under APSL-1.1 and APSL-1.2 (some
IOKit families, parts of hfs) are accepted like APSL-2.0. CDDL, a file-level license that
is not GPL, is accepted only for the DTrace files that ship inside XNU, so the kernel
keeps DTrace. No other CDDL code enters the tree.

### ADR-23 — WebKit and JavaScriptCore

**Accepted.** Parts of Apple's WebKit and JavaScriptCore are LGPL, so they never enter
this repository and nothing depends on them (ADR-24). The default system provides
`JavaScriptCore.framework` and `WebKit.framework` at Apple's paths as our own
implementations of their public APIs over permissively licensed engines, as S30
specifies. Apple's LGPL WebKit may be built in a separate repository and installed under
`/Library/Optional/`; by dyld's search rule (S14) an optional package is used only where
the system provides no framework at that install name, so it never replaces ours.

### ADR-24 — Permissive first

**Accepted.** The system does not rely on GPL or LGPL software. Wherever a permissively
licensed implementation exists or can be written, the design uses it; no tier, wave exit
or part of the default image depends on GPL or LGPL code. GPL or LGPL software may be
offered only as an optional extra, from a separate repository and channel, beside a
permissive default. The accepted licenses are extended with BSL-1.0, CC0, the FreeType
license (FTL), the libpng license, 0BSD, the X11 license, the bzip2 license, the IJG
license, the libtiff license, the zsh license, the curl license, the Less license, the
SCOWL license and the OpenSSL/SSLeay license, all permissive. MPL and other file-level copyleft
licenses are not accepted, except CDDL for XNU's DTrace files (ADR-22).

### ADR-25 — Patent-encumbered codecs

**Accepted.** H.264, HEVC/HEIC and AAC are patent-encumbered. Until counsel approves a
licensing route, the default image ships no decoder or encoder for them; the APIs that
would use them return their documented unsupported-format errors, which S23 and S27
specify. Permissively licensed, royalty-free formats (AV1, VP8, VP9, Opus, Vorbis, FLAC,
MP3, PNG, JPEG, WebP) are supported.

### ADR-26 — License for our own code

**Accepted.** Everything written for this project is BSD-2-Clause: every file carries
`SPDX-License-Identifier: BSD-2-Clause`, and the license text is the root `LICENSE`
file. Patches to vendored files keep the license of the file they change (APSL-2.0 for
XNU, BSD for FreeBSD and OpenBSD drivers).

*Considered:* BSD-3-Clause, used until now — the third clause (no endorsement) adds
nothing the project needs. Apache-2.0 and BSD-2-Clause-Patent — both add an explicit
patent grant from contributors. BSD-2-Clause has none; if contributions from companies
make an explicit patent grant necessary, moving to BSD-2-Clause-Patent is a one-line
change per file that keeps the same terms otherwise and stays compatible with GPLv2 for
the driver kit (S11).

### ADR-27 — PureDarwin as a seed source

**Accepted.** PureDarwin's code may seed ravynOS components under the rules in
[PUREDARWIN-SEEDS.md](PUREDARWIN-SEEDS.md): each file is taken only under its own stated
license, with "MPL-2.0 OR BSD-2-Clause" files taken as BSD-2-Clause; MPL-2.0-only,
GPL, LGPL, CDDL and unlicensed files are not taken; taken code is vendored with
`_PROVENANCE` and patches like any upstream; PureDarwin's in-place XNU edits are re-cut
as reviewed patch series; and its architecture (Nix build, Wayland display path,
stubbed services) is not adopted. Code is taken only when it is a native implementation that meets
SYSTEM-DESIGN section 2.7; code that only imitates an Apple interface, takes shortcuts,
or carries no license header is not taken, and the component is written natively with a
better design. The headerless IOUSBFamily files already in the tree are rewritten this
way (GAP-42). The kernel, driver and audio work it provides
shortens S06, S09, S10, S11 and S27 the most.

### ADR-28 — Built the way Apple builds macOS

**Accepted.** Every subsystem is designed and written the way Apple's engineers design
and write the corresponding part of macOS: IOKit's driver model and lifecycle, XNU's
kernel conventions, Libsystem and libdispatch idioms, Mach, MIG and XPC for IPC, Cocoa's
API conventions and memory rules, launchd and bundle packaging, `os_log` logging. The
details are SYSTEM-DESIGN section 2.7. Two reasons: Mac software depends on the
behavior those conventions produce, not only on the symbol names, and engineers who know
macOS can read, review and extend code that follows them. The review gate (section 2.7)
enforces it.

### ADR-29 — Commit identity

**Accepted.** All commits are authored and committed as the project owner. No commit
carries an AI tool's name, email, co-author trailer or session link, and no commit
message describes how a change was produced. Agents working on this repository set git's
`user.name` and `user.email` to the owner's identity before committing.
